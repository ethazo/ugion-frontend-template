# 架构设计

## 分层

自下而上四层,依赖只能向下,不能反向或跨层回指。

```
app/        应用装配:入口、Provider 栈、角色注册表、启动引导
routes/     路由文件,只做装配(与 app/ 同属装配层)
features/   业务功能,按功能垂直切分
layouts/    布局,按布局形态划分(非按角色)
shared/     通用能力:UI 组件、请求层、工具、hooks、类型
styles/     全局样式与主题 token,不含逻辑
```

依赖方向规则:

- `shared/` 不依赖任何上层,也不包含业务概念
- `layouts/` 可用 `shared/`,不直接依赖具体 feature 的内部实现
- `layouts/` 中不出现角色判断,布局不知道谁在用它
- `features/*` 之间**禁止互相 import**,共享内容下沉到 `shared/`
- `styles/` 不被 import(除入口引一次 `global.css`),它只产出 CSS 变量
- 只有 `app/` 与 `routes/` 可以同时看到所有层

`features/*` 互不引用这条用 ESLint 规则强制,不靠自觉。

## 启动引导

认证基于 Cookie / Session,前端读不到 httpOnly cookie,因此**无法在客户端判断登录态**。应用启动时必须先问后端。

```
挂载
  └─ 请求当前用户 GET /api/auth/me
       ├─ 401         → 跳登录页
       ├─ 成功        → 拿到 user 与 role
       │                  └─ 按 role 查注册表 → 重定向到该角色落地路径
       └─ 网络/5xx    → 错误页,提供重试
```

这个请求是整个应用的第一道关卡,在它返回之前不渲染任何业务界面,只显示启动态。三种结果必须都有明确去向,不能让应用停在空白页。

会话中途失效(后端返回 401)由请求层统一拦截,清理本地用户状态并跳登录页,不在各处自行处理。

## 角色分发

### 注册表与路由树的分工

用文件式路由,路由树由 `routes/` 目录结构生成,**不能**由注册表动态拼装。因此两者职责分开:

| 关注点                                   | 归属               |
| ---------------------------------------- | ------------------ |
| 有哪些路由、嵌套关系                     | `routes/` 目录结构 |
| 角色标签、落地路径、选用哪个布局、导航项 | 角色注册表         |

新增一个角色要动两处:在 `routes/` 下建该角色的目录,在注册表加一条记录。这是文件式路由的固有代价,换来的是类型推导和路由自动生成。

### 注册表内容

一份角色到元信息的映射,集中在一个文件:

```ts
{
  student: { label: '学生',   landing: '/student', layout: 'top-nav', nav: [...] },
  teacher: { label: '教师',   landing: '/teacher', layout: 'top-nav', nav: [...] },
  admin:   { label: '管理员', landing: '/admin',   layout: 'sidebar', nav: [...] },
}
```

角色标识不在业务代码里手写成联合类型字面量,而是从一处推导。

### 角色标识放哪

这里有个依赖方向问题需要交代清楚。接口响应要用 Zod 校验 `role` 的取值,而校验发生在 `features/auth/api.ts`;如果取值来自 `app/roles.ts`,feature 就向上依赖了装配层,违反分层规则。

所以拆成两层:

| 内容                                                        | 位置            | 谁用                         |
| ----------------------------------------------------------- | --------------- | ---------------------------- |
| 角色标识集合(`['student','teacher','admin']`)与 `Role` 类型 | `shared/types/` | 请求层校验、注册表、路由校验 |
| 角色元信息(标签、落地路径、布局、导航项)                    | `app/roles.ts`  | 装配层                       |

`Role` 类型从标识集合推导,Zod 用同一个集合建 enum,注册表的 key 也受它约束——三处共用一个来源,新增角色改 `shared/types/` 一处,其余位置的类型错误会把该改的地方全部暴露出来。

大小写转换(后端 `ADMIN` ↔ 前端 `admin`)也放这一层,见 `06-api-contract.md`。

注意 `layout` 是一个**选择**,不是归属。学生和教师同选 `top-nav`,复用的是同一个布局组件,不存在两份近似代码。哪天某个项目要让教师改用侧边栏,改这一行即可。

### 路由级校验

每个角色的路由段在 `beforeLoad` 中校验当前用户角色,不匹配则重定向到该用户自己的落地路径。这样即使有人手输 URL 也进不去别的角色区域。

前端校验只是体验层面的分流,**不构成安全边界**。真正的权限判断在后端,前端不假设自己拦得住。

## 布局

布局解决的是登录后每个页面都要有的那些东西:用户是谁、怎么退出、怎么切主题、怎么导航。

**布局按自身形态划分,不按角色划分。** 这是一条关键约定:布局是独立的功能单元,只描述"内容怎么排",不知道也不关心哪个角色在用它。角色通过注册表选择布局,布局内部没有任何角色分支。

模板内置两种:

| 布局      | 形态                | 适用                             |
| --------- | ------------------- | -------------------------------- |
| `top-nav` | 顶部导航 + 全宽内容 | 入口较少、以阅读和流程为主的界面 |
| `sidebar` | 侧边菜单 + 内容区   | 入口较多、需要多级导航的界面     |

新增布局就是往 `layouts/` 加一个目录,和已有布局平级,不牵动角色逻辑。

### 插槽划分

每种布局内部都由三个插槽组成:

```
┌──────────────────────────────────────┐
│  导航区              │    用户区     │
├──────────────────────┴───────────────┤
│                                      │
│              内容区                  │
│                                      │
└──────────────────────────────────────┘
```

- **用户区**:内容确定且所有角色一致——头像、姓名与身份、主题切换、退出登录。一个共用组件,两种布局都直接放进去,只是摆放位置不同。
- **导航区**:布局决定导航怎么摆(横排还是竖排、是否支持多级),导航项内容由注册表传入。布局不硬编码任何具体入口。
- **内容区**:承载路由出口,布局不干预内部结构。

这样切的结果是三者各自独立变化:用户区改一处对所有布局生效;导航形态换布局即可;内容区完全归各页面自己。

第一版两种布局实现得朴素即可,先把结构立住,视觉后期再调。

## 主题与暗色模式

Tailwind v4 的 `@theme` 直接产出原生 CSS 变量,因此主题切换就是在根元素上切换一组变量值,不需要额外的样式方案。

模式偏好存本地,初始值跟随系统。要注意首次渲染前就把 class 写到 `html` 上,否则会闪一下亮色。

## 数据流

- 服务端数据统一走 TanStack Query,不自行用 `useEffect` 拉数据
- 接口响应在边界用 Zod 校验后再进入应用,不信任后端一定按约定返回
- 客户端状态只用于外壳级 UI(主题、侧栏折叠这类),业务数据不放 Zustand

## 部署形态

单一构建产物,三套外壳共存其中。前后端同域,生产环境不需要跨域配置;开发环境由 Vite 代理转发 API,否则本地 cookie 带不上。

产物需支持部署在子路径下,因此构建时的 base 路径可配置,应用内不出现硬编码的绝对路径。
