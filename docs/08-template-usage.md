# 模板使用说明

## 定位

这个模板解决的是架构和外壳层面的问题:分层约定、角色分发、布局与用户区、请求层、主题机制。业务内容由各项目自己填。

模板不试图预测业务形态。如果发现某个项目需要改动模板的核心结构才能推进,那是模板的边界划错了,应该反过来修模板。

## 起一个新项目

1. 用 GitHub 的 "Use this template" 或直接 clone 后删掉 `.git` 重新初始化
2. 改 `package.json` 的 `name`
3. 复制 `.env.example` 为 `.env.local`。默认值指向现有后端,换后端才需要改 `VITE_API_PROXY_TARGET`
4. `pnpm install`
5. `pnpm dev`

模板自带的示例页面可以直接删掉,它们只是为了让骨架跑得起来。

## 改造清单

新项目通常要动这几处,按顺序:

**角色**。改 `app/roles.ts`。角色标识、显示名、落地路径、选用的布局、导航项。角色数量不是三个也没关系,注册表是数据不是硬编码。

**布局选择**。在注册表里给每个角色指定 `top-nav` 或 `sidebar`。如果两种都不合适,在 `layouts/` 下加一个新的,与已有的平级,不要改现有布局去适配。

**视觉风格**。改 `styles/global.css` 里的 token 值。颜色、圆角基准、字体栈。因为组件只引用语义 token,改完全站生效,不用碰组件代码。

**接口对接**。在 `features/*/api.ts` 里加业务接口的 schema 和调用函数。`shared/api/` 的请求层和错误约定不用动——响应包装、401 处理、`success` 判定对同一套后端是通用的。只有换到响应形状不同的后端时才改它。

**页面**。在 `features/` 下加功能目录,在 `routes/` 下加对应路由文件。路由只做装配。

## 跟进模板更新

模板后续会改进,已经克隆出去的项目怎么跟上。

现实做法是:**不做自动同步**。加一个 remote 手动挑选提交:

```bash
git remote add template <模板仓库地址>
git fetch template
git log template/main --oneline    # 看有哪些改动
git cherry-pick <commit>           # 只挑需要的
```

不建议 merge 整个模板分支——业务代码和模板代码交织之后,合并冲突的处理成本远超收益。

哪些值得挑回来:请求层的 bug 修复、布局的可访问性改进、依赖的安全更新。哪些不必:模板的示例代码调整、与你项目无关的新布局。

反过来,如果在某个项目里改出了通用的改进,回流到模板仓库,别只留在项目里。这是模板保持有用的唯一途径。

## 边界

模板明确不包含:

- 测试与 CI
- 具体业务组件与页面
- 业务接口。认证、当前用户、文件三类基础接口已按真实后端接好(见 `06-api-contract.md`),业务接口各项目自己加
- 权限的细粒度控制。前端只做角色级路由分流,真正的权限判断在后端
